Request publication

Requester: complete the form

  • Describe the business purpose, capabilities, and AI use during development or at runtime.
  • Supply the repository, owner/risk answers, requested date (YYYY-MM-DD), and environment (dev, test, or prod).
  • Confirm: no sensitive content, guide read, and responsibility for completing controls with evidence.

Maintainer: review before processing and approval

Check completeness, real calendar dates, and attestations, including legacy/API-created or edited issues that may omit them. The form UI is not an enforcement boundary.

Description, date, environment, and attestations stay in the source issue; they are not tier inputs or copied to generated issues. Dev/test never lowers risk, deadlines never waive controls, and attestations are not security evidence.

These metadata fields do not change the plan fingerprint (a hash of risk answers and applicable control requirements). Edits still invalidate advisory approval; every /publish run clears it. See when controls need manual reopening.

Request change or re-assessment

Requester: link the original request and affected controls. Compare changed purpose, data, exposure, audience, privileges, hosting, or runtime AI; explain evidence impact, accountable team, and requested date. A different solution repository needs a new publication request.

Governance: decide what needs fresh evidence

ChangeRequired action on the original request
Parsed risk answers, applicable controls, or evidence work packages changeUpdate answers and rerun /publish. Required existing controls reopen automatically.
Metadata-only change; risk answers/requirements unchanged (for example, model behavior changes while AI stays Yes)Assess evidence impact and manually reopen affected controls. Rerunning /publish alone leaves completed controls closed.
  1. Verify the same-hub original link. Authorized hub collaborators' reassessment opened/edited/reopened events clear its advisory readiness/approval labels and add an audit comment. Invalid links fail visibly; public requesters cannot trigger this action. No solution-repository write occurs.
  2. Reopen the original request if needed; record the change and update its answers. Do not label the reassessment publication-request or run commands there: that would create a separate plan.
  3. A maintainer comments /publish on the original. Existing issue IDs are reused; only missing applicable controls are created. Historical controls remain for audit. Follow the table above for reopening.
  4. Complete refreshed controls, /validate the original, and obtain a new human decision before release. Record links/outcome in the reassessment, then close it.

Every /publish clears prior advisory approval. Unchanged reruns neither duplicate controls nor automatically reopen completed controls.

Request re-assessment

Request a control exception

Use one request per exact catalog control ID. Link the original request and generated control issue. Explain the justification, residual risk, compensating controls and safe evidence, proposed expiry, and the accountable risk owner.

  1. Governance validates the scope, date, mitigations, and authority of the named risk owner. The daily lifecycle sweep maintains one comment on tracked open or closed exception records that are missing/invalidly linked, expire within seven days, or are expired. The reminder is visibility only; it does not infer approval, renewal, or an active waiver.
  2. The accepting authority and governance explicitly record approval or rejection, scope, conditions, expiry, and remediation owner. Closing a request by itself is not approval. Link the decision from the original request and control issue.
  3. Track implementation, remediation, renewal, and revocation manually. Renewal requires a fresh review. On expiry, the waiver no longer applies; reassess or stop the affected activity through the protected release/operations process.

No bypass: An exception does not change tiering, close generated issues, or convert FAIL/UNKNOWN to PASS. The stock gate continues to report its gaps. Any separately authorized manual production decision must say explicitly that automatic readiness was not achieved; never present an accepted waiver as a clean automated report.

Request decommission

Link the original request, identify the solution repository and accountable retirement team, propose a date, and document user impact, communications/migration, resources/access, and data retention/disposal. If no original request exists, explain that rather than inventing a link.

  1. Business, technical, platform, data owners, and governance review the plan, rollback needs, retention, legal holds, and required approvals before destructive action.
  2. Authorized operators execute the approved retirement: disable deployments and federation where appropriate, revoke unnecessary access/credentials, retire cloud resources and integrations, and verify billing, monitoring, DNS, data migration, and lawful disposal. The toolkit does none of this automatically.
  3. Record safe evidence and owner confirmation. Governance removes readiness/production approval from the original request, records its retirement, and closes it to end the daily validation sweep. Preserve tracking issues, decisions, and required audit records rather than deleting history.
  4. Close the decommission request only when agreed work and evidence are complete. Treat any later revival as a new governance decision.

Maintainer routing rules

Lifecycle labels never trigger publication-plan generation; do not add publication-request. Commands on lifecycle forms do not run intake or validation. Separate housekeeping clears advisory labels for authorized reassessments and adds scheduled exception reminders. Checkboxes and date prompts support review, not authorization or date validation.
