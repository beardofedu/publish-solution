Default · implemented

Path A: reviewed readiness package, platform-owned deployment

  1. A citizen developer submits a structured request in the governance hub. A maintainer reviews scope, allowlists the exact solution repository, and runs the authorized intake.
  2. The toolkit creates a stable parent/control issue set in that repository. Each control includes its lead/supporting roles, useful prerequisites, steps, acceptance criteria, evidence checklist, examples of sufficient and insufficient evidence, and a guide link.
  3. Owners add safe evidence references, complete controls, and ask for validation on the original request. Repository checks are bound to a default-branch commit; a branch change during validation fails the run. FAIL and UNKNOWN remain blocking.
  4. The generated handoff records source request, repository, risk tier, control status/evidence locations, validation time and commit basis, open gaps, and explicit pending fields for the human governance decision and separate platform acceptance.
  5. A named governance reviewer verifies the evidence and records approve/reject/defer, rationale, residual risks, conditions, and expiry. A named platform owner separately accepts the deployment boundary, environment, rollback, and operations responsibility.
  6. The customer platform team independently deploys under its protected release controls. New scope, changed evidence/commit, expired exceptions, or changed policy require reassessment and fresh review.

Prepared means the machine assembled a package. Reviewed means a named human inspected evidence and recorded a decision. Accepted means the platform owner explicitly accepted the operational handoff. These states are not interchangeable and none is inferred from a label.

A Low tier is not an exemption: it still requires every applicable baseline control and evidence review. Marking an environment prod is human context, not an automatic tier change; platform owners must still verify production identity, network, data, monitoring, rollback, and release protections.

The automation cannot prove live Azure identity, network, data handling, alert remediation, evidence quality, or deployment. Reviewers must verify those with the responsible owners. Reviewer responsibilities · Reassessment, exception, and retirement routing.

Optional · reference only

Path B: Azure deployment starter references

These examples are deliberately incomplete, non-production, and not connected to an executable deployment workflow. They are prompts for a customer platform team to design its own solution. Do not paste real tenant, subscription, client, or resource identifiers into the public example.

Identity and trust boundary

  • Use a separately governed deployment identity with the smallest resource scope. Prefer workload identity federation over a stored client secret when supported by the organization.
  • Constrain federation to the intended repository and protected environment/branch claims. Verify the effective subject, issuer, and audience in the actual issued token and Azure trust configuration; do not infer trust from YAML text.
  • Keep the CI identity distinct from the application's runtime identity. Grant the runtime identity only required data/service permissions; store unavoidable runtime secrets in an approved vault.
  • Require protected-environment review and branch policy before production credentials become available. Keep break-glass access separately governed and audited.

Service selection questions

Choose a hosting service only after documenting workload shape, network/data requirements, region, scale, supported runtime, identity features, availability objectives, and the platform team's operating model. A simple web/API workload may fit a managed web or container service; event-driven workloads may fit a serverless service. Validate current feature and regional availability with Azure documentation and the landing-zone owner before deciding.

Prerequisites, cost, and rollback ownership

  • Prerequisites: approved Azure landing zone, subscription/resource-group ownership, region/data policy, network design, identity registration/federation, security baseline, monitoring, backup and incident contacts.
  • Cost: estimate hosting, compute/scale, storage, network egress, logs/retention, security features, backup/replication, and model/API consumption where applicable. Confirm billing dimensions, quotas, alert thresholds, and who responds. Budgets/alerts may notify rather than hard-stop spend; verify service-specific controls and current pricing.
  • Rollback: platform owner defines the immutable previous artifact/configuration, data/schema compatibility, rollback trigger, recovery objective, verification steps, and decision authority. Practice in non-production; application/data owners assess irreversible changes.

Reference boundaries: Azure identity and deployment conversation. This repository does not create Azure resources or validate their live state.

Optional · reference architecture only

Path C: protected release integration

Use this design when a customer release service consumes readiness evidence. Keep the release decision inside an independently protected system, not a GitHub issue label or a generated comment.

  1. Bind evidence to immutable inputs. Record source request ID, solution repository, exact reviewed commit, control-catalog/policy version, build artifact digest, environment, and timestamp. Reject unknown, missing, mismatched, or stale values.
  2. Separate duties. The requester cannot approve their own release. Governance verifies policy/evidence; the platform owner verifies environment and deployment boundary; a protected environment/release authority independently permits the deployer.
  3. Revalidate at the decision boundary. Immediately before release, fetch current request/policy and evidence state again, ensure the exact commit and artifact are unchanged, confirm all required checks passed, and confirm no new request edits, open reassessment, expired exception, revoked approval, or changed permissions.
  4. Make revocation effective. A new commit, scope edit, catalog/policy change, evidence withdrawal, failed check, exception expiry, or reviewer revocation invalidates the prior decision. Revoke queued deployment authorization where possible; do not rely on daily sweeps to stop an immediate release.
  5. Fail closed and preserve audit. If the evidence API is unavailable, identity differs, state cannot be read, or a time-of-check/time-of-use race is detected, stop before credential access. Record who decided, the evidence digest, decision time, failure reason, and any later manual recovery.

Threats the integrating platform must handle

  • Issue labels and text are mutable, and issue closure does not prove evidence quality.
  • Evidence can become stale between reviewer approval and deployment; bind the approval to a commit and artifact digest and verify again at execution.
  • Approvals can be revoked or the requester may change the target after review; re-read and compare exact scope at the release boundary.
  • Concurrent requests, duplicated callbacks, API outages, expired tokens, changed team membership, and partial deployment need idempotency, safe retry, and explicit rollback behavior.
  • A static workflow pattern cannot attest Azure federation, live permissions, network boundaries, or successful rollback.

This is a design checklist, not a supplied policy engine. Any implementation must be threat-modeled, independently reviewed, and tested against stale evidence, revocation, and TOCTOU cases before production use.

Host boundary: the stock toolkit targets GitHub.com. GHES and GHEC data-residency hosts require specific API, action, identity, feature, and Pages adaptations plus a host-specific pilot. Documentation examples are not evidence of support.
