From an empty hub
to your first publication plan.

Install a governance repository your organization controls. A citizen developer creates a solution repository, opens a request in your hub, and the hub's Actions create the plan in that solution repository.

This walkthrough is the installation path through the existing enterprise readiness runbook, not a second sign-off checklist. Use its sign-off record for approvals and restricted evidence, and SETUP.md for the configuration reference at your deployed commit.

Install the toolkit, not an Azure workload. No Azure subscription, resources, OIDC identity, cloud credentials, Copilot seat, or workflow in a solution repository is required merely to generate issues. Workflows and credentials for later deployment belong to the workload's separate release process. The stock validator does inspect an Azure OIDC workflow pattern; an issue-generation pilot can succeed while workload readiness remains blocked.

2. Adopt an independent, customer-controlled hub

Responsible: organization owner and platform maintainer. First approve Actions for only the intended repositories at the enterprise and organization levels; keep the new hub excluded from running Actions during bootstrap. At organization > Repositories > New repository, create publish-solution. Choose Private for selected-team access, or Internal only if enterprise-wide read access is acceptable. For a Git import, leave README, license and .gitignore initialization off so the destination is empty.

Recommended adoption: a reviewed Git copy into that independent repository. A fork of this public upstream remains public and cannot independently change visibility. Do not fork publicly and add confidential content. Managed users cannot fork outside their enterprise; enterprise policies can further restrict forks. An approved template-generated independent copy is another option only if the chosen source is configured as a template. Retain the MIT license, upstream URL and reviewed commit. Sources: fork restrictions and visibility.

Optional CLI: create a private empty hub and prepare a one-way Git copy

Use this instead of UI creation, not in addition. Enterprise policy must keep Actions disabled for this destination until bootstrap review is complete. Use a fresh local directory outside any existing customer checkout.

gh repo create contoso/publish-solution --private --disable-wiki
git clone --single-branch --branch main https://github.com/beardofedu/publish-solution.git publish-solution-install
cd publish-solution-install
git rev-parse HEAD
git remote rename origin upstream
git remote set-url --push upstream DISABLED
git remote add origin https://github.com/contoso/publish-solution.git
# Review the commit and bootstrap changes described below before the first push.
# After approved local changes are committed:
git push -u origin HEAD:main

The push URL guard reduces accidental upstream writes; it is not an access control. Do not use mirror/force pushes for routine updates or put credentials in remote URLs.

Before the first push, review the imported workflow files. Keep Pages unpublished: remove the push trigger from the adopted .github/workflows/pages.yml until step 8 is approved, retaining workflow_dispatch for an intentional launch. Make bootstrap changes without credentials, push the reviewed copy, then use protected pull requests for subsequent changes. If using a default branch other than main, update the CI and Pages branch filters and source links. Intake/validation explicitly check out the repository's trusted default branch.

Upstream strategy: assign a maintainer to fetch reviewed upstream commits and propose internal update PRs. Review workflow pins, dependencies, policy and catalog changes, resolve local customization conflicts, and repeat the pilot. Never automatically mirror either direction or export customer policy/history to the public upstream. An independent Git copy does not synchronize issues, settings, labels, secrets, variables or App installations.

Expected success: contoso/publish-solution contains the trusted implementation, has the approved visibility, and has no credentials or unintended published guide.

3. Protect the hub, configure access, then enable Actions

Responsible: hub administrator, security owner and platform maintainer. Apply protections before adding the App key. Recommended controls below must be configured by administrators; the toolkit does not install them.

  1. In hub > Settings > General > Features, enable Issues. In organization > Teams, create or select platform maintainers and governance reviewers. In hub > Settings > Collaborators and teams, grant maintainers the minimum command-capable role. Give citizens enough read access to discover the guide and open/comment on requests, not hub write access just to bypass preflight. Confirm actual enterprise/base permissions with an ordinary pilot user.
  2. Replace upstream .github/CODEOWNERS ownership with your explicit-write-access teams. Protect workflows, scripts, package manifests/lockfile, policy, tiers, controls, docs and CODEOWNERS itself. In hub > Settings > Rules > Rulesets > New ruleset > New branch ruleset, target the default branch, enable enforcement, require PRs/reviews and code-owner review, and restrict bypass. Require the toolkit checks once they have run. Two owners on one CODEOWNERS line do not require two independent approvals. See GitHub's owner requirements.
  3. Review enterprise Policies > Actions, then organization > Settings > Actions > General, then the hub's Settings > Actions > General. Higher-level policy wins. Approve the exact full-SHA uses: references in the deployed workflows and their dependencies. The stock hub uses actions/checkout, actions/setup-node and actions/create-github-app-token; optional Pages adds actions/configure-pages, actions/upload-pages-artifact and actions/deploy-pages. Enterprise-only action policy can block even GitHub-authored actions. Do not relax SHA pinning to make a run pass.
  4. Keep restrictive default workflow-token permissions. Intake and validation explicitly request contents: read and issues: write for the hub; verify policy permits these. No PR-approval capability is needed. Enable the approved hub in organization Actions policy and repository settings. No target workflow is needed for issue generation.
  5. The bundled jobs use ubuntu-latest. Approve GitHub-hosted runners or adapt runs-on through review for an isolated, maintained, preferably ephemeral runner. Check the runner version required by every pinned action's runtime, not just the job's Node.js 22 setting. Permit GitHub API, action/runtime downloads, npm and CI's Go module access. Never share the credential-bearing runner with untrusted solution builds, or execute target code with hub credentials.
  6. Create the hub labels in hub > Issues > Labels > New label: publication-request, approved-for-production, reassessment-request, control-exception and decommission-request. Assign human triage for the three manual lifecycle forms; their labels do not trigger automated processing and must not be combined with publication-request. The toolkit creates risk/readiness labels as needed; it does not require control labels in solution repos.

Run the existing checks on the adopted copy; no GitHub credentials are needed:

npm ci --ignore-scripts
npm test

Expected success: only approved maintainers can change trusted automation, required labels exist, and Actions > Toolkit checks passes. Intake and validation retain the same publish-solution-mutations concurrency group and cancel-in-progress: false. See Actions policy and the existing foundation policy review.

Responsible: citizen developer/solution owner, with the organization repository administrator. In organization > Repositories > New repository, create team-helper with approved private/internal visibility and initialize a default branch with a harmless README. If enterprise policy prevents creation, use the normal repository-request process; do not grant enterprise admin. At solution repo > Settings > General > Features, enable Issues and confirm the repo is active, not archived or disabled.

Assign the solution team enough access to work and close its issues; assign independent reviewers appropriate access to evidence. The solution owner also needs access to open a request in the hub. Keep the hub and solution repositories distinct.

gh repo create contoso/team-helper --private --add-readme --disable-wiki

5. Register and install an organization-owned GitHub App

Responsible: organization owner or authorized App manager; organization owner approves installation. Use the same organization for this first pilot. The stock workflows mint a token for one installation owner, not a token spanning organizations.

  1. Open profile picture > Your organizations > contoso > Settings > Developer settings > GitHub Apps > New GitHub App. Choose a unique service name and an approved support/homepage URL such as your hub URL.
  2. This App is an installation-token identity only. Leave OAuth user authorization and device flow off; no callback or webhook service is needed. Under Webhook, deselect Active. Native hub issue/comment events trigger the workflows, not App webhook subscriptions.
  3. Under Repository permissions, configure the stock profile below. Leave unnecessary organization/account permissions and event subscriptions off.
  4. For this organization-owned, single-org App, choose Only on this account under installation availability, then Create GitHub App. Record the App ID, not the installation ID or client ID.
  5. On the App's General page, under Private keys, choose Generate a private key. Handle the downloaded PEM using approved secure storage. Do not paste it into a request, commit, screenshot or command argument.
  6. In the App settings choose Install App > Install beside contoso, then Only select repositories > team-helper > Install. Do not select the hub merely to process hub issues: its built-in token handles those. Record the selected installation without recording bearer tokens.

Optional CLI: set App variables and upload a securely stored key

Replace the App ID placeholder. The file path is a placeholder for approved secure storage; never create a PEM in this repository.

gh variable set SOLUTION_APP_ID --repo contoso/publish-solution --body 'APP_ID_FROM_REGISTRATION'
gh variable set SOLUTION_APP_OWNER --repo contoso/publish-solution --body 'contoso'
gh variable set SOLUTION_APP_REPOSITORIES --repo contoso/publish-solution --body 'team-helper'
gh secret set SOLUTION_APP_PRIVATE_KEY --repo contoso/publish-solution < /approved/secure/path/app-private-key.pem

An organization Actions secret is an alternative if its selected-repository access includes the hub. An environment secret will not be available to these jobs unless you deliberately adapt the jobs to use that environment; github-pages is not the intake environment. The runtime names HUB_TOKEN and SOLUTION_TOKEN are workflow mappings, not extra repository secrets. HUB_TOKEN receives github.token; SOLUTION_TOKEN receives the minted App token or the PAT.

Alternative: approved fine-grained PAT

If an App is unavailable, document the exception, accountable user, expiry/renewal owner and migration plan. Open profile picture > Settings > Developer settings > Personal access tokens > Fine-grained tokens > Generate new token. Select resource owner contoso, a policy-approved expiration, Only select repositories > team-helper, and the repository permissions in step 5. Complete required organization approval and applicable membership/SSO requirements. The user's real permissions still constrain the token.

Store the token in the hub as SOLUTION_REPO_TOKEN; gh secret set SOLUTION_REPO_TOKEN --repo contoso/publish-solution prompts for it without a literal secret in shell history. Leave SOLUTION_APP_ID unset and remove unused credentials. Precedence: the workflow attempts App authentication whenever the App ID is set; token selection is App output first, PAT second. A failed App step stops the job; it is not a reliable or intended PAT failover. Choose one mode and repair broken App setup rather than leaving a spare PAT to conceal it. Do not use a broad classic token to bypass policy.

Expected success: the hub has exactly the chosen credential path; secret values are not visible in the repository or evidence. One App installation token or fine-grained PAT resource owner does not support arbitrary multi-org requests. Use separate hubs or implement and test explicit per-owner routing before expanding. Source: PAT permissions and limitations.

7. Allowlist the target and adapt the policy and guide

Responsible: governance/security owners and platform maintainer. Through a reviewed hub PR, edit config/policy.yml. The empty default allowlist denies all targets, including repositories the App can access. Use exact owner/name entries, not a wildcard or organization name:

allowed_repositories:
  - contoso/team-helper
guide_url: https://APPROVED-GUIDE-HOST/BASE-PATH
requester_permissions: [admin, maintain, write]
scan_max_age_days: 30

Replace guide_url with the actual approved guide root, without a page filename. The placeholder is not a working URL; private Pages URLs must be copied from Settings, not guessed. Keep the upstream public guide only if your policy explicitly permits it and no internal guidance is needed. Repository installation selection, token scope and this allowlist must all cover the same approved target.

Review config/tiers.yml and controls/*.yml against your internal policy. Keep stable control IDs and supported fields; edit the corresponding docs/controls.html anchors and evidence requirements together. If changing intake choices, update scripts/model.mjs, the issue form, rules, tests and guides together. See CUSTOMIZING.md for the supported schema and changed-catalog behavior; use the existing policy mapping register rather than inventing an extra checklist.

In .github/ISSUE_TEMPLATE/request-publication.yml, adapt the public-instance warning to the actual approved audience while preserving the prohibition on secrets/sensitive data. Update .github/ISSUE_TEMPLATE/config.yml contact links, the request button in docs/index.html, and repository-specific links throughout HTML and Markdown to your hub/default branch/guide. Keep upstream links only where they intentionally cite upstream. Test as a citizen so a request cannot accidentally land in the public upstream.

Run npm test and npm run check for policy/catalog changes. Expected success: approved configuration is on the trusted default branch; team-helper is authorized explicitly; guide anchors and customer-hub links resolve.

8. Optionally publish the guide to an approved audience

Responsible: organization owner, documentation/platform owner and security reviewer. Pages is not needed to generate issues. If it is not approved, keep the Pages push trigger removed and its workflow disabled at hub > Actions > Publish guide > workflow menu > Disable workflow. Use an approved authenticated host for the static docs/ files, and set guide_url accordingly.

  1. For Cloud private publishing, confirm an organization-owned private/internal project repository and GitHub Enterprise Cloud entitlement. In organization > Settings > Member privileges > Pages creation, permit privately published sites. A private repo does not automatically mean a private website. Without EMU, Pages can be public or private; EMU only permits private sites and enterprise-member access. Verify your intended audience.
  2. In hub > Settings > Pages, choose GitHub Actions under Build and deployment > Source and set GitHub Pages visibility to private before publishing confidential content. If the required private option is unavailable, stop and use an approved authenticated host, not a public pilot with internal content.
  3. Approve the pinned Pages actions and review Settings > Environments > github-pages for the intended branch/reviewer policy. The Pages workflow uses contents: read, pages: write and id-token: write; that OIDC permission is for Pages, not Azure.
  4. Enable Actions > Publish guide if disabled, then choose Run workflow on the approved default branch. It publishes plain HTML/CSS from docs/, with no site generator or external assets. After access review, restore the reviewed docs-push trigger if automatic updates are desired.
  5. Copy the actual site URL from Settings > Pages > Visit site. Test an intended reader, an unauthorized signed-in user and an unauthenticated session. Confirm the actual denied/allowed results; update guide_url and guide links through review. Private project-site access normally follows repository read access, so granting guide access also grants hub read access.

Expected success: the approved audience can read the guide, unintended readers cannot, and generated links point to the correct host. Reuse Pages gate 5 for access evidence and separate GHES considerations. Sources: organization Pages policy and Pages access prerequisites.

9. Prove the citizen-to-issues flow with synthetic data

Responsible: citizen developer, hub maintainer and independent governance observer. Use the selected disposable repository and ordinary user roles, not only an org admin session. Record request, run, parent/control issue URLs and the deployed configuration commit in the existing sign-off record.

  1. As the citizen, open contoso/publish-solution > Issues > New issue > Request publication. Enter contoso/team-helper, fictional team aliases, Internal data, Internal exposure, Small team, runtime AI No, None or read-only integrations, and hosting Undecided. Add a synthetic solution description covering purpose and AI behavior, a real requested date in YYYY-MM-DD format, and target environment dev. Read and truthfully accept the requester attestations, then submit. These additional fields are human-review context, not tier inputs or validation waivers; the maintainer must review them. Under unchanged stock rules this is Low; determine the expected applicable control IDs from your deployed catalog before running.
  2. Confirm the open hub request carries publication-request. Authorized hub collaborators' opened/edited/reopened issue events can process automatically. For a non-collaborator, preflight rejects processing before minting a target token; a failed run here is expected. A maintainer with a configured permission must review the target/answers and post a new comment containing exactly /publish on the hub request. Permission in the solution repo alone does not authorize the command. Editing an old comment is not the command trigger.
  3. Open hub > Actions > Publication intake, select the run and inspect preflight, token creation and issue-generation steps. Follow the hub bot comment to the target. Expect exactly one [Publication] Production readiness (Low) parent and one child issue per applicable catalog control, with criteria, evidence guidance, prompts, source backlink and working guide links. With the unchanged stock catalog and runtime AI No, this is 11 control issues plus one parent; recompute for a customized catalog. Risk labels appear on the hub. Native sub-issue links are attempted; 403/404/410/422 produces an explicit task-list fallback. Other API errors stop the run. Validation uses the catalog and issue markers, not manually ticked boxes.
  4. Post a fresh /publish comment with unchanged answers. Expect the same parent and child issue IDs, not duplicates. Preserve generated HTML markers and the hub bot's state comment. If a run partly creates issues then fails, inspect the cause and rerun the command; markers recover missing work. Do not delete/recreate issues or cancel active intake. Both mutation workflows serialize together; a burst can replace a pending run, so reconcile missing commands.
  5. Have the maintainer comment exactly /validate on the same hub request. Inspect Actions > Validate publication readiness and the report on the request/parent. With open controls and an undeployed fixture, expect Publication gaps remain, no ready-for-review, and no automatic approval. A successfully executed workflow may still report readiness gaps: inspect the report, not only the Actions status.
  6. In the disposable pilot, change runtime AI to Yes or exposure to External and rerun intake as authorized. Expect the derived tier/applicable controls to change, required existing controls to reopen for fresh evidence and new controls to appear without a second parent. Stock reruns clear previous advisory readiness/approval; unchanged control IDs are reused. Historical controls no longer required remain for audit. Changing the target needs a new request.

This does not mean the solution or enterprise is production-ready. Record these as the issue-generation subset of the existing pilot matrix; do not mark unexecuted workload tests as passed.

Continue separately to workload readiness and human review

Required control issues must be closed as completed, with evidence; not planned/duplicate closure does not satisfy the gate. Every stock automated check must PASS. FAIL and UNKNOWN both block readiness; permissions, missing features, stale scans or truncated trees do not become passes. The stock validator has no automatic exception override, and its Azure-specific OIDC pattern check remains required even when hosting is Other cloud or Undecided. Do not add a dummy deployment workflow merely to make validation green. Implement and test an approved equivalent detector or keep readiness blocked with a separate human risk decision.

Use the control guide, Azure workload guidance and Azure readiness gate 4 when actually preparing a workload. When all required issues and checks pass, the hub gets ready-for-review. An independent governance reviewer examines evidence and records a human decision; applying approved-for-production is manual. The toolkit does not enforce exclusive reviewer authority over mutable labels. Issue closure, labels and configuration signals are neither compliance certification nor production authorization; protect real deployments independently.

11. Maintain, rotate and safely pause the service

Responsible: platform/service owner, credential owner and security operations. Use the existing operations contract for alerting, backups, audit evidence, incident response and maintenance cadence. Monitor failed/stuck intake and validation runs, App selection/permission changes, Actions policy and runner changes, and aging requests.

Keep requests open while monitoring readiness. Stock validation schedules a sweep of open labeled requests at 07:17 UTC daily; Actions > Validate publication readiness > Run workflow also sweeps them. Schedules may be delayed. API outages can even prevent label cleanup, so stale labels must never unlock deployment.

Rotate App keys on your approved schedule: generate a replacement, securely update SOLUTION_APP_PRIVATE_KEY, prove intake/validation on the pilot, then revoke the old key after checking other consumers. App keys do not automatically expire. For PATs, renew before expiry, review effective user/repo access and approval, update the secret, retest and revoke the obsolete token. Track primary and backup owners; never print token values in evidence. Source: App private-key management.

Review upstream, action and dependency updates as internal PRs, preserve pins and concurrency, run the existing checks and repeat representative tier/idempotence/denial tests. Record the new deployed commit. Policy/catalog changes can invalidate old plans and require /publish to reopen controls; communicate this before rollout.

Planned pause or retirement

  1. Announce the pause and stop inviting new requests; update the hub form/contact guidance. Let active intake finish during a planned pause rather than cancelling it mid-creation.
  2. In hub > Actions, open Publication intake and Validate publication readiness in turn; use each workflow's menu > Disable workflow. Disable Pages separately if needed. Disabling a workflow does not undo prior writes or necessarily stop an already running job.
  3. For containment or retirement, an authorized administrator suspends/uninstalls the affected App installation in organization App settings, or revokes the PAT, following incident policy. Remove obsolete hub secrets once dependency checks are complete. In a compromise, prioritize containment over waiting for a run. Deleting a private key alone does not establish that previously minted installation tokens are gone.
  4. Retain requests, target issues, markers, state and audit evidence; do not mass-close them to indicate success. Review any old approval labels and actual deployment permissions independently. Disabling the service neither unpublishes an existing Pages site nor revokes a workload's cloud identity. Unpublish/restrict Pages explicitly under Settings > Pages if required.
  5. Before resuming, reconcile partial requests, restore reviewed configuration and credentials, re-enable the selected workflows, repeat the synthetic pilot and reassess stale approvals.
Optional CLI: pause future intake and validation triggers
gh workflow disable intake.yml --repo contoso/publish-solution
gh workflow disable validate.yml --repo contoso/publish-solution

These commands do not revoke credentials, stop all active runs, unpublish Pages or remove generated issues.

Expected success: service ownership and rotation are durable, pauses stop future automation deliberately, and existing evidence remains intact.

Troubleshoot without broadening access blindly

Start with hub > Actions > the relevant run > failed step and the hub request report. Preflight/token-creation failures may only be visible in Actions logs. Use run URLs and sanitized error details, never keys/tokens or sensitive issue bodies, in support tickets.

Observed symptom, likely boundary and safe next action
SymptomInspect and correct
Form missing or no intake runCheck default-branch workflow/form files, Issues/Actions policy, the publication-request label and event filters. Adding only the label later is not an intake trigger; have an authorized maintainer post a fresh exact /publish.
Non-collaborator/preflight denialCheck the actor's effective hub permission against requester_permissions. Route a reviewed request to a maintainer; do not widen citizen permissions to avoid the check.
Action blocked / runner waits or runtime failsInspect overriding enterprise/org allow policies, full-SHA pins, runner labels/version, network and npm/Go access. Do not disable policy or execute untrusted code on the privileged runner.
