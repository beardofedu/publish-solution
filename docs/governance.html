Trust evidence, not checkboxes

A review gate.
Not a rubber stamp.

The toolkit separates preparation, automated signals, and human risk acceptance. It never deploys a solution or grants production approval.

Who can do what?

RoleResponsibility
Citizen developerSubmit the request, complete the solution-repository issues, and collect evidence. Non-collaborators can submit requests but cannot trigger privileged cross-repository writes.
Governance maintainerAllowlist exact target repositories, configure narrowly scoped credentials, and authorize /publish or /validate. Default accepted hub permissions: write, maintain, admin.
Security / platform / data ownersReview controls in their area, verify live cloud settings, and approve or reject exceptions.
Production reviewerInspect the report and evidence, confirm residual risks, and apply approved-for-production. Enforce the real release decision through independently protected deployment environments.

Read the automated report correctly

PASS means the specific signal was observed. FAIL means a required condition was not met. UNKNOWN means permissions, plan, API visibility, or another limit prevented verification. Both FAIL and UNKNOWN block ready-for-review.

  • All currently applicable control issues must exist and be closed as completed. “Not planned” and “duplicate” do not pass.
  • The API checks secret scanning/push protection settings, Dependabot alerts, a recent successful default-head code scanning analysis, applicable pull-request approval protection, substantive CODEOWNERS/SECURITY.md, .env filenames, and an Azure OIDC workflow pattern.
  • These checks do not verify alert dispositions, full Git history, cloud configuration, workflow enablement, actual deployment, bypass actors, or the quality of evidence.
  • Scheduled validation runs daily on open requests. Keep requests open while tracking readiness. Request changes and control catalog changes require a fresh intake, which reopens required controls. A new target repository requires a new request.
Readiness is a point-in-time signal. A target commit, issue, permission, or cloud configuration can change after a report. Daily checks can lag; closed requests are not revalidated. Labels are advisory and mutable by repository collaborators. Do not build a production authorization boundary around these labels.

Use the handoff package as a record, not an approval

Validation generates a package with the original request, target repository, risk tier, applicable control issues/evidence locations, automated status, UTC timestamp, and default-branch commit used. A second branch read detects commits that land while checks run and fails validation if the head changed. The package lists linked time-bound exceptions for visibility; it does not decide whether an exception was accepted or let it bypass a failed/unknown check.

Prepared means the tool assembled a current report. Reviewed requires a named governance reviewer to inspect evidence and record approve/reject/defer, rationale, residual risks, conditions, and expiry. Accepted is a separate platform-owner record confirming the environment, release boundary, rollback, and operations owner. The generated decision fields stay PENDING; neither a label nor issue closure fills them. An edited/reopened source request or authorized reassessment invalidates the previous report and advisory labels. Before release, re-check scope, current commit, evidence freshness, exception expiry, and protected environment state.

Reviewer checklist

  1. Confirm the classification, audience, integrations, runtime AI, hosting, target environment, requested date, attestations, and owners are truthful and current. Dev/test metadata never lowers the tier; a requested date never overrides review.
  2. Inspect each control's evidence. Issue closure alone proves nothing about security posture.
  3. Review scanner findings, secret rotation, dependencies, identity scopes, data lifecycle, and live cloud controls.
  4. For High risk, confirm independent security and applicable privacy/compliance sign-off.
  5. Record approval or rejection with safe evidence links and named authority. Apply approved-for-production only as a human decision record, then use the protected release process.

Handle exceptions explicitly

If a feature is unavailable, or a non-Azure deployment uses an equivalent identity pattern, document the gap, compensating controls, accepting authority, expiry, and review date. The stock automated gate does not turn an exception into a PASS. Governance may separately record a manual decision, or customize a reviewed detector/policy and its tests. Never close an issue to hide an exception.

Review lifecycle requests

Use the publication lifecycle forms and manual review runbooks for scope changes, exceptions, and retirement. Reassess changes through the original publication request to preserve idempotent markers; clear prior approval during review. Exceptions never bypass the automated gate, and decommission requests never perform destructive actions. Each manual request has its own label; do not add publication-request to it.

Check the publication description, requested date, dev/test/prod environment, and required attestations during human review. They are recorded in the source issue only, excluded from automated tiering and the plan fingerprint, and do not relax controls. The form UI requires them, but legacy/API-created or edited issues may omit them; verify manually.

Keep the automation safe

Use an exact repository allowlist and selected-repository App installation or PAT. Protect policy, workflow, and script changes with reviews. Workflows use trusted default-branch code and never execute target repository code. Treat issue text, repository files, and model output as untrusted. Do not add a privileged workflow that checks out a requester's branch.
